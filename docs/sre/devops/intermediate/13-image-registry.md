## 前言

承接 [12 ｜ 持续集成流水线](ci-pipeline.md) 的产出——源代码被构建为容器镜像——下一步必然会面对：

*   镜像推送到哪里？谁来拉取？
*   多个 CI 源都在推镜像，版本号怎么约定才不冲突？
*   出了问题怎么追溯"这个镜像到底是从哪个 commit 构建的"？

本系列把制品治理放在这里，**而不是**把它混入更宏观的"高级篇"——因为它是 CI 与 CD 之间的必要衔接，不解决它，CD 流水线就没有可信输入。

> 注：本系列曾有一篇独立的"私有镜像仓库治理"文章，已于 2026-09-08 移入 `_archive/`，本篇为重写版本，定位与结构完全不同。

## 一、镜像仓库的角色定位

仓库不是"网盘"，而是 CI 与 CD 之间的**可信交接点**。这一节明确制品仓库在流水线中的位置，以及它与代码仓库、日志、监控的边界。

## 二、镜像 tag 与版本策略

镜像 tag 决定了版本可追溯性。本节给出基于 `commit SHA + 时间戳 + 构建号` 的最小 tag 方案，以及为什么不应该用 `latest`。

## 三、本系列仓库选型

## 四、镜像签名与不可变

镜像一旦推送就不应被覆盖（不可变原则）。本节给出 retention 策略、tag 锁定、与后续 SBOM（高级篇 19）的衔接点。
