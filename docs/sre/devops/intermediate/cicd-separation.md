## 构建通过不等于可以发布

一个镜像可以经过测试，但目标环境可能没有容量，或数据库还不兼容。CI 与 CD 分离的价值，是让构建结果和发布决定各有明确输入、权限与证据。

个人项目中可以由同一个人承担两种职责，也可以把两个阶段放在同一个工作流。分离不要求两个部门、两个平台或每次都人工审批。

## 制品是交接契约

| 阶段 | 输入 | 输出 | 权限 |
| --- | --- | --- | --- |
| CI | 确定的源码 commit、依赖和构建配置 | 经过测试的镜像 digest、报告与来源记录 | 读取源码、写目标镜像仓库 |
| CD | 已批准的制品和配置、目标环境 | 实际发布版本、验收和恢复记录 | 读取制品、变更指定环境 |

同一制品从 dev 晋级到 prod 时不重新构建。镜像 digest 用于识别内容，签名用于验证身份；不能把 MD5 或一个标签当作可信来源保证。

## 责任按能力与场景划分

开发维护应用行为、测试与部署声明；平台维护执行环境、权限和可观测能力；发布责任人确认目标与验收条件。实际可由一个团队共同承担，也可按组织要求分工。

故障归因需要查看应用、基础设施、配置和流程证据，不预设“所有生产故障运维全责”。CI 与 CD 都可能并行或串行，执行模型取决于依赖关系，不是两者的定义差异。

## 一个可落地的边界

- PR 仅运行检查，不读取生产密钥。
- 合并受保护分支后构建并推送镜像，保存 digest。
- 发布申请固定镜像和配置版本，按风险决定自动准入或人工审批。
- CD 验证来源、部署、检查健康，失败保持失败并保留诊断信息。
- 发布记录关联执行身份、版本、环境和结果，保留周期按实际要求确定。

正式实施时，用独立账号测试“CI 无法修改生产、CD 无法覆盖镜像”；只在架构图上画两个框不算完成分离。

## 最小验收与思考

提交代码后只看到 CI 运行，生产版本没有改变；发布失败可以查到具体 digest 和恢复记录；无需重新构建就能把 staging 验证过的制品交给生产。
