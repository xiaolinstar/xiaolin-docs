# 设计文档：03/04 篇对调与 Git·GitHub 文章重写

## 背景与问题

当前基础篇顺序为：

1. 01 ｜ Nginx 静态资源代理
2. 02 ｜ 生产环境入门：部署到云服务器
3. 03 ｜ Git 与 GitHub：版本管理与服务器构建
4. 04 ｜ 服务端应用部署：依赖、运行时与进程保活

用户反馈 03 篇存在三个问题：

1. **生产发布痛点不清晰**：「scp vs git pull」的对比更像个人偏好，没有先给出 build-in-server 的真实痛点。
2. **场景更像个人开发者**：企业生产服务器通常不会直接从 GitHub 拉代码，当前写法对运维读者缺乏说服力。
3. **主题不够明确**：文章把「喜欢用 git pull 不喜欢 scp」包装成最佳实践，但本质上是开发者工作流。

## 设计目标

- 把 Git/GitHub 的引入时机放到「服务端应用部署」之后，让它成为解决「构建不可追溯」问题的工具，而不是前置的运维必修课。
- 明确文章重心：**Git 和 GitHub 是开发者必须熟悉的两个工具和网站**；运维人员需要理解它们，因为后续所有部署与流水线都建立在代码版本管理之上。
- 弱化「服务器 git pull 是最佳实践」的表述，强化「版本管理本身的价值」和「Git/GitHub 最小用法」。

## 方案概述

采用「方案 A：03 与 04 对调」。

新顺序：

1. 01 ｜ Nginx 静态资源代理
2. 02 ｜ 生产环境入门：部署到云服务器
3. 03 ｜ 服务端应用部署：依赖、运行时与进程保活
4. 04 ｜ Git 与 GitHub：版本管理与云端仓库
5. 05 ｜ 容器 Docker
6. 06 ｜ 流水线基础
7. 07 ｜ GitHub Actions
8. 08 ｜ 多服务容器编排
9. 09 ｜ 基础篇总结

## 风险与回退

- 风险：外部文章或读者已记住旧序号。缓解：文章 frontmatter 中的 `date` / `updated` 保持不变，通过内容本身让读者感知新顺序。
- 风险：搜索引擎已收录旧 URL。缓解：文件名不变，仅标题和序号变化，URL 不受影响。
- 回退：若后续发现对调后衔接不顺，可回退到方案 C（保留位置、重写定位），只需再改一次标题和索引。
