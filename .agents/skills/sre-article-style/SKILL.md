# SRE / DevOps 系列文章写作风格规范

本技能约束 `docs/sre/**` 下所有系列文章的开篇与章节标题写法,确保读者从「上一篇文章」到「下一篇文章」感受不到风格切换。

---

## 1. 章节标题:不带中文序号

**规则**:所有二级及以上标题(`##`、`###`)**禁止**使用「一、二、三」「1. 2. 3.」「(一)(二)」等序号格式。

**反例**:
```markdown
## 一、Docker 网络命名空间

### 1.1 默认行为为什么一开始能用?

## 二、Compose 网络的最小可用形态
```

**正例**:
```markdown
## 网络命名空间:被混用的隔离边界

### 默认行为为什么一开始能用

## Compose 网络的最小可用形态
```

**为什么这样写**:
- 中级篇读者已经在基础篇积累「无序号」的阅读惯性,序号出现会让人感觉「是不是新文章」
- 标题本身就是「这段要回答什么问题」,信息密度足够,序号是冗余
- 跨文章引用时,带序号的标题在重排时容易乱

---

## 2. 引言:直接带场景/痛点

**规则**:文章第一段(标题下的内容)必须**直接呈现一个真实场景或痛点**,让读者在前三行知道「这篇要解决什么问题」「和我有什么关系」。

**禁止的开篇模式**:

| 反例 | 问题 |
|---|---|
| `本篇将介绍 XXX 的基本概念与使用方法` | 抽象,与读者无关 |
| `Docker 网络是容器化部署的重要知识点` | 套话,任何文章都能套 |
| `本文从三个方面分析 XXX` | 编号式预告,实为大纲前置 |
| `## 一、引言 / ## 一、本篇目标` | 结构化开场,打断阅读流 |

**推荐的开篇模式**:

| 模式 | 示例 |
|---|---|
| **场景化痛点** | 「你有一台 2C4G 的服务器,跑着博客 + API + 一个开源工具的自部署。`docker compose up` 突然报 `port is already allocated`……」 |
| **承接上一篇** | 「基础篇 08 篇你跑过这套闭环。当一台服务器开始跑多个项目,这套闭环就开始出问题了。」 |
| **现象 → 错误归因** | 「`curl localhost:8080` 在容器里不通,大多数人会先去查配置文件。其实问题不在配置——`localhost` 在容器里指的不是宿主机。」 |

**关键约束**:
- 第一段**不**写「本篇将……」「本文……」「下面介绍……」这种结构化预告
- 第一段**不**用「一、二、三」式分点
- 第一段**必须**有具体场景、具体数字、或具体命令失败现象

---

## 3. 章节过渡:用承接句,不靠序号

**规则**:章节之间用承接句过渡,而非靠「一、」序号强制衔接。

**反例**:
```markdown
## 二、Compose 网络的最小可用形态

## 三、网络边界怎么切
```

**正例**:
```markdown
## 网络的最小可用形态

理解了 namespace 这一层,Compose 提供的工具就清晰了——它们都是「给 namespace 命名 / 切分 / 显式连通」的操作。

## 网络边界的三种典型场景

一个项目内可能需要内外网分离,多个项目间又要避免串味,稀缺端口又得规划——三种场景的处理思路完全不同。
```

## 5. 反例自检清单

写完一篇文章后,过一遍:

- [ ] 文章开篇前 3 行有没有具体场景、具体数字、具体失败现象?
- [ ] 是否还有 `## 一、` `## 二、` 形式的章节标题?
- [ ] 是否还有 `### 1.1` `### 2.3` 形式的小节标题?
- [ ] 「本篇将……」「本文……」「下面介绍……」有没有出现在第一段?
- [ ] 章节之间有没有承接句,而不是靠序号强制衔接?
- [ ] 最后有没有给下一篇留一个「伏笔」(下一篇文章要解决什么)?

## 6. 长代码与分步骤讲解

涉及较长代码、嵌套配置或多文件调用时，读取 [代码拆解方案集合](references/code-decomposition.md)。先明确读者用途，再选择整体骨架、逐层展开、阶段讲解等结构；生成候选效果后由作者决定修改原文还是分发方案。不得按行数机械切块，长命令与块长度分别评审；明确片段、完整文件与执行条件。

## 7. 代码示例的语言

- 自编或实质修改的程序、脚本与配置示例，注释、日志、参数校验提示、报错提示和教学占位文本默认使用简洁、准确的英文。注释说明意图与约束，避免逐行复述；较长解释放在代码块外，用中文讲解。
- 英文化不得改变控制流、变量名、接口协议、引号、转义或运行行为。实际业务数据、需要中文编码验证的测试数据、原样命令输出及第三方引用保留原意，不机械翻译。
- Mermaid 等面向中文读者的图表标签、正文、图注不受程序示例英文要求约束。作者明确指定的教学例外优先。
- 既有文章不自动批量改写；作者指定的文章及后续实质编辑的相关示例同步执行。历史评审材料保持可追溯，不为统一语言覆盖原始记录。

## 8. 文章结构规范

系列文章（`docs/sre/**`）应包含以下标准结构，确保内容完整性和跨篇一致性：

| 章节 | 必需 | 说明 |
|------|------|------|
| **引言** | ✅ | 直接呈现场景/痛点，承接上一篇预告（如有） |
| **正文** | ✅ | 多个章节，用承接句过渡，不靠序号衔接 |
| **流程旁白** | ✅ | 说明本篇的视角边界和适用场景 |
| **小结** | ✅ | 100–150 字，概括核心结论 |
| **思考** | ✅ | 3 个问题，引导读者深入理解 |
| **延伸阅读** | ✅ | 2 个主题，每个主题附推荐阅读链接 |
| **参考** | ✅ | 3–5 条参考资料，编号 + 标题 + URL |

**结构顺序**：引言 → 正文 → 流程旁白 → 小结 → 思考 → 延伸阅读 → 参考

**与公众号稿件的关系**：Origin 是权威原文，包含完整结构；公众号稿（`content/dist/{slug}/wechat.md`）做适当降级——保留「小结 → 延伸阅读 → 参考资料」，「思考」可融入正文或省略，尾部追加「下篇预告 + 问题 + 原文入口」。详见 `wechat-publisher` SKILL.md。
