# Content Review - 技术文档百分制白盒复盘

## 边界（先讲清楚）

**本 SKILL 是白盒复盘工具**，用于内部迭代改进——发现具体问题、给出优先级、让作者知道怎么改。

**本 SKILL 不决定发布门槛**。发布门槛由独立的黑盒评价层决定（异源模型 + subagent 包装，本评分规则对作者**不公开**，避免"应试作文"问题）。

> 黑盒层未接入前，本 SKILL 的分数仅作**内部基线**。

## 输入

- `file`（必需）：Markdown 文件路径（项目内相对路径）
- `depth`（可选）：`quick` | `standard` | `thorough`，默认 `standard`
  - `quick`：5 维度各扫一遍，10 分钟内完成
  - `standard`：每个维度完整跑检查清单
  - `thorough`：除 standard 外，额外做跨文章一致性、新引入术语校对

## 输出

- 总分（0-100）+ 评级（优秀/通过/未通过）
- 5 维度分项得分
- 问题清单（按 P0/P1/P2 分级，含位置、问题、建议）
- 改进优先级排序

## 评分维度

| 维度 | 满分 | 关注点 |
| --- | --- | --- |
| 结构与节奏 | 20 | 章节层级、过渡、节奏、信息密度 |
| 内容质量 | 25 | 准确性、完整性、深度、可读性 |
| 表达严谨性 | 25 | 数学/概念严谨、术语一致、无歧义、无重复 |
| 可操作性 | 15 | 命令可执行性、失败应对、跨平台、最小验证清单 |
| 格式与术语 | 15 | 命名、加粗兼容、shortcode、glossary、索引 |

## 评分规则

每个检查项的打分采用**离散等级**（避免主观性）：

| 等级 | 分值 | 含义 |
| --- | --- | --- |
| 完全满足 | 满分 | 该项完美达标 |
| 基本满足 | 满分的 80% | 有小瑕疵但不影响整体 |
| 部分满足 | 满分的 50% | 满足一半，需修复 |
| 严重不足 | 满分的 20% | 几乎不满足 |
| 完全缺失 | 0 | 该项完全没做 |

**示例**：维度 1 第 2 项（章节层级合理，3 分）：

- 8 个 `##`、4 个 `###`，合理 → 3 分（满分）
- 12 个 `##`、过多但可读 → 2.4 分（80%）
- 6 个 `##` 但顺序混乱 → 1.5 分（50%）

**特殊规则**：
- P0 问题出现 1 个 → 该维度封顶 80%
- P0 问题出现 2+ → 该维度封顶 60%
- 这是为了"硬错误必须修复"的强制约束

## 评级阈值（v1.3 校准）

| 分数 | 评级 | 含义 |
| --- | --- | --- |
| ≥ 90 | 优秀 | 可直接发布 |
| 85–89 | 通过 | 微调后可发布 |
| < 85 | 未通过 | 必须打磨后重评 |

### 按文章类型细分阈值（基于 7 篇样本校准）

| 文章类型 | 建议门槛 | 理由 | 代表 |
| --- | --- | --- | --- |
| **入门文章** | 80 | 入门文章可操作性弱是合理的，不应过度扣分 | 01 |
| **进阶/工程文章** | 85 | 工程文章要求严谨性与可操作性 | 02、03、04、05、07、08 |
| **形式化 / DAG 等重数学** | 88 | 形式化表达准确性是核心 | 03、06 |
| **综述类文章** | 80 | 综述类可操作性维度要求低，重点是覆盖度 | 09 |

### 阈值上调依据（v1.3）

7 篇样本分数：86 / 92 / 99 / 94.5 / 94.5 / 91.5 / 94 / 94 / 86

- 中位数：92
- 均值：91.9
- 标准差：≈ 4.5

**结论**：原 80 分门槛过松（多数文章在 90+），上调到 85 更合理。同时允许不同文章类型有不同门槛。

## 详细检查清单

### 维度 1：结构与节奏（20 分）

| 分值 | 检查项 |
| --- | --- |
| 3 | frontmatter 完整（title/description/date/updated/category/tags） |
| 3 | 章节层级合理（一篇 `###` 不超过 6 个，`##` 不超过 8 个） |
| 3 | 有清晰的开头（点题）与小结（呼应） |
| 4 | 章节之间有过渡，不直接跳 |
| 4 | 信息密度均匀（无大段空话，无过度堆砌） |
| 3 | 思考题呼应正文（不多不少，梯度合理） |

### 维度 2：内容质量（25 分）

| 分值 | 检查项 |
| --- | --- |
| 5 | 概念定义首次出现即清晰 |
| 5 | 跨文章一致（同一概念表述统一，无矛盾） |
| 5 | 有足够的深度（不浮于表面，有递进） |
| 4 | 案例真实可重现（命令、文件、参数都是真实存在的） |
| 3 | 错误信息/边界情况有提及 |
| 3 | 不堆砌术语（每个术语有解释或锚点） |

### 维度 3：表达严谨性（25 分）

| 分值 | 检查项 |
| --- | --- |
| 5 | 数学/形式化表达准确（公式、符号、定义无错） |
| 4 | 没有绝对化或夸张表述（"根治"、"一定"、"永远"等需限定） |
| 4 | 没有歧义或自相矛盾 |
| 4 | 没有重复内容（同观点在多段反复强调，扣分） |
| 3 | 中英之间空格（参照 `.agents/rules/core.md`） |
| 3 | 称谓统一（"你"或"您"，不混用） |
| 2 | 引号使用正确（弯引号 `""`、嵌套用 `『』`） |

### 维度 4：可操作性（15 分）

| 分值 | 检查项 |
| --- | --- |
| 3 | 命令可直接复制执行（占位符明确标识） |
| 3 | 失败时的应对给出（curl、健康检查、日志命令） |
| 3 | 跨平台/版本差异标注（Ubuntu 版本、价格时效） |
| 3 | 有"最小验证清单"（发布后如何确认成功） |
| 3 | 代码块包含必要上下文（路径、参数、版本） |

### 维度 5：格式与术语（15 分）

| 分值 | 检查项 |
| --- | --- |
| 3 | 术语用 `{{term:xxx}}` shortcode（首次出现） |
| 3 | 新术语已入库 `docs/glossary/`（用前先建） |
| 3 | 加粗兼容（中文标点不阻断，参考 `core.md`） |
| 2 | 弯引号 + 加粗结合规范（`"**强调**"`） |
| 2 | 文档索引同步（`docs/.vitepress/config.mts`） |
| 2 | 代码块 vs 行内代码使用合规（参考 `core.md`） |

## 执行步骤

1. **通读全文**：理解文章定位、读者画像、主旨（避免按规则机械打分）
2. **扫描 frontmatter**：检查字段完整性、日期合理性
3. **列出结构**：所有 `##` 与 `###`，审视层级与数量
4. **逐维度检查**：按 5 个维度的清单逐项打分
5. **汇总**：总分 + 各维度 + 问题清单 + 优先级
6. **输出报告**：按下方模板

## 报告模板

```markdown
# Content Review: `<file>`

**总分：XX/100** — <评级>

| 维度 | 得分 | 满分 |
| --- | --- | --- |
| 结构与节奏 | XX | 20 |
| 内容质量 | XX | 25 |
| 表达严谨性 | XX | 25 |
| 可操作性 | XX | 15 |
| 格式与术语 | XX | 15 |

## P0（必须修复，不修不发）

- [维度X] **第 N 行**：<问题>。建议：<具体改法>。

## P1（建议修复，影响总分 5+）

- ...

## P2（可选打磨，影响总分 2+）

- ...

## 改进优先级

1. 先做 P0（必修复）
2. 再做 P1（性价比高）
3. 最后做 P2（锦上添花）
```

```markdown
# Content Review: `docs/sre/devops/foundation/delivery-start.md`

| --- | --- | --- |
| 结构与节奏 | 16.5 | 20 |
| 内容质量 | 21 | 25 |

## P0（必须修复，不修不发）

- [可操作性] **第 184、320 行**：`sudo systemctl restart nginx` 配置未变就用 restart 是浪费，应该 `nginx -t && systemctl reload nginx`（reload 不中断服务）。建议：改为 reload。

## P1（建议修复，影响总分 5+）

- [结构] **二级标题过多（**12 个 `##`）**：拆分/合并——"配置文件结构"、"代理自定义页面"、"理解 root 指令" 可合并为"配置与代理"一章；"安装 VitePress"、"本地调试、构建与预览"可合并为"开发闭环"。

## 改进优先级

1. **先做 P0**（不修 restart → reload 不发）
2. **再做 P1**（合并章节 + 加失败排查表 + Nginx 简介加深）——这三项预计从 86 上 92+
3. 最后 P2（锦上添花）
```

## 错误处理与边界情况

| 情况 | 处理方式 |
| --- | --- |
| 文件不存在 | 立即报错退出，列出可用的同目录文件供选择 |
| 文件不是 `.md` 后缀 | 警告但仍尝试解析（允许非标准后缀） |
| 文件超过 50KB | 提示"建议拆分为多篇"，但仍执行评价 |
| frontmatter 完全缺失 | 维度 1 自动扣 3 分；在报告中明确指出 |
| frontmatter 字段不完整 | 列出缺失字段；不重复扣分（按"完全缺失"打 0 分） |
| 文章内未使用任何 term shortcode | 维度 5 不重复扣分（按设计，可能全文无术语） |
| 文章内有未入库的术语 | 列入 P0："术语 X 已使用但未入库 docs/glossary/" |
| 跨文章引用了未发布的文章 | 提示"目标文章未发布，跨文章一致性检查降级" |

**关键边界**：本 SKILL 不做"否决权"——任何错误都不直接阻止文章发布，只在报告中标注。最终发布门槛由黑盒层决定。

## 使用注意

1. **不要照搬分数阈值**：阈值是临时基线，跑 ≥ 5 篇后**必须重新校准**
2. **不要被规则反向利用**：作者不应**针对本 SKILL 的检查项优化**——黑盒层才是发布门槛
3. **跨文章一致性**：对照系列其他文章，避免同一概念表述不一致
4. **术语源头唯一**：每术语全站只在一处首次解释，其他文章用 `{{term:xxx}}` shortcode
5. **数学/概念正确性**：本 SKILL 不深入评判（留给未来的"概念审查"专项 SKILL）

## 双轨评价体系（白盒 + 黑盒）

本 SKILL 是**白盒层**，作者可见，用于内部改进。**黑盒层**独立运行，作者不可见，用于发布门槛。

```
┌────────────────────────────────────────────┐
│           双轨评价                          │
├────────────────────────────────────────────┤
│ 白盒层（content-review，本 SKILL）         │
│   - 作者可见                                │
│   - 详细问题清单                            │
│   - 用于迭代改进                            │
│   - 权重：30%                              │
├────────────────────────────────────────────┤
│ 黑盒层（blackbox-review，未来）            │
│   - 作者不可见                              │
│   - 独立模型 + subagent 包装                │
│   - 只给总分，不给规则                      │
│   - 权重：70%                              │
└────────────────────────────────────────────┘
```

最终发布门槛分 = `白盒分 × 0.3 + 黑盒分 × 0.7`

### 黑盒层设计骨架（占位实现）

**接口契约**：

```python
def blackbox_review(article: str, platform: str) -> BlackboxResult:
    """
    黑盒评价
    
    Args:
        article: 文章完整 Markdown 内容
        platform: 目标平台（"wechat" / "blog" / "docs"）
    
    Returns:
        BlackboxResult {
            score: 0-100,
            reason: str,  # 一句话理由，不超过 50 字
            model: str,   # 评估模型标识
        }
    """
```

**Prompt 模板**（关键设计：不透露本项目规则）：

```
你是一位 <platform> 平台的主编，请评估下面这篇文章的发布价值。
只考虑读者体验：这篇文章是否值得读者花时间阅读？
请打 0-100 分，并给出一句话理由（≤ 50 字）。

<article>
{article_content}
</article>

输出格式：
分: <0-100>
理由: <一句话>
```

**关键约束**：
- ❌ 不告诉评分维度（结构/内容/表达/可操作/格式）
- ❌ 不告诉阈值（80/90）
- ❌ 不告诉本项目规则
- ❌ 不告诉是哪个模型在评估

**调用方式**：
- 用 `Agent` 工具派发给 subagent
- subagent 隔离上下文，避免主会话干扰
- 模型选择：与 Claude 异源（如 GPT-4 / Gemini / DeepSeek）

**未来接入步骤**：
1. 实现 `blackbox-review` 子 SKILL（独立文件）
2. 配置异源模型 API 接入
3. 双模型基线校准（用 ≥ 10 篇样本做分数对齐）
4. 接入外部阅读数据做长期回归

## 与其他 SKILL 的协同

### 调用顺序

```
Step 1: markdown-formatter（格式修复）
Step 2: content-review（本 SKILL，白盒 30%）
Step 3: blackbox-review（黑盒 70%）
Step 4: 加权平均：最终分 = 白盒 × 0.3 + 黑盒 × 0.7
Step 5: 与发布阈值（80）对比，决定发布
```

### 调用细节

| SKILL | 阶段 | 可见性 | 调用方式 |
| --- | --- | --- | --- |
| **markdown-formatter** | 修复格式 | 作者可见 | 当前会话直接调用 |
| **content-review**（本 SKILL） | 内容评价 | 作者可见 | 当前会话直接调用 |
| **blackbox-review** | 黑盒评价 | 作者不可见 | **必须用 subagent 隔离调用** |

**关键约束**：blackbox-review 的 subagent 必须隔离上下文，避免主会话已读到的本 SKILL 内容（评分维度、阈值等）污染黑盒评分。

### 黑盒层未接入前

如果 blackbox-review 还没接入实际模型，最终分暂用**仅白盒分**：

```
最终分（暂定）= content-review 分 × 1.0
```

待 blackbox-review 接入后切换为加权平均。

## 校准流程

每跑 5 篇样本后：

1. 收集分数分布（每个维度、总分）
2. 识别异常分数（某维度普遍偏低/偏高）
3. 调整权重或阈值
4. 在 SKILL frontmatter 标注 `calibrated_at: <日期>` 与样本数
5. 把校准记录写进"实测样本"小节，便于追溯
