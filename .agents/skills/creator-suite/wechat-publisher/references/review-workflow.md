# 公众号静态检查与人工审核

审核结果保存在文章分发目录的 `wechat-review.json`，与 `meta.yaml` 中的 `draft / ready / published` 发布状态分开。状态均不能替代微信粘贴、保存重开和手机预览的实际验收。

| 状态 | 含义 | 是否写入正式 HTML |
| --- | --- | --- |
| `failed`：不通过 | 有结构错误，或尚未获人工认可的 SLA 例外 | 否，保留已有正式稿 |
| `passed`：通过 | 当前静态检查未发现问题 | 是 |
| `manual_passed`：人工通过 | 仅有 SLA 例外，且作者明确认可当前版本的全部例外 | 是 |

“通过”仅覆盖脚本已实现的静态检查：固定抬头图、唯一 H1、标题层级、正文不混入操作标题，以及摘要 120 字、代码块 20 行/单行 72 字符、图注 40 字。表格、列表、图幅、图片体积、CDN 可用性、内容真实性和微信端显示仍按格式集合核对，不能据此宣称全部 SLA 或发布验收已通过。

## 操作流程

1. 运行 `node scripts/render-wechat.mjs content/dist/{slug}/wechat.md`。结构或 SLA 检查失败时，报告列出问题 ID、行号与阈值；脚本非零退出，不覆盖 `wechat.html`。
2. 结构错误须修复；SLA 超限先向作者展示实际内容、阈值与影响，由作者选择修改稿件、调整通用规范，或保留本次例外。不能代替作者同意，也不因过去另一篇稿件通过而自动认可。
3. 作者明确认可具体例外后，在报告的 `approval` 中记录以下字段。复用本报告的哈希和问题 ID，审核人、理由、时间均按真实反馈填写：

```json
{
  "source_hash": "本报告 source_hash",
  "policy_hash": "本报告 policy_hash",
  "issue_ids": ["本报告中获认可的 SLA 问题 ID"],
  "reviewer": "实际审核人",
  "reason": "认可例外的理由及用户反馈依据",
  "reviewed_at": "实际审核时间（ISO 8601）"
}
```

4. 再次运行同一渲染命令；仅当稿件、渲染相关元数据（摘要、来源 URL、slug）、渲染入口及规则一致、所有例外均获认可，才记为 `manual_passed` 并生成正式 HTML。只修改 `status` 不会放行；稿件或规则变化后旧认可失效。单独调整 `meta.yaml` 中的发布状态或 checklist 不影响审核结果。报告与正式稿一起保留，每篇仍只有一份 `wechat.html`。

已有格式的验收范围继续有效；本流程只记录当前稿件的静态检查与具体例外，不新增微信发布授权。备用 `render-wechat-native.mjs` 使用相同检查与报告机制，其排版仍须按原有验收边界核对。
