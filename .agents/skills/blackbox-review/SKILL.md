# Blackbox Review - 黑盒评价层

## 定位

黑盒评价是**双轨评价体系**的另一极，与白盒的 content-review 配合：

```
最终分 = content-review 分数 × 0.3 + blackbox-review 分数 × 0.7
```

| 层 | 作者可见 | 用途 | 权重 |
| --- | --- | --- | --- |
| **content-review**（白盒） | ✅ 可见 | 内部迭代改进 | 30% |
| **blackbox-review**（黑盒） | ❌ 不可见 | 发布门槛 | 70% |

**核心防御机制**：白盒让作者知道为什么扣分，但黑盒让作者无法针对性优化。

## 边界（关键）

**黑盒层对作者完全不可见**——SKILL 文件、Prompt 模板、模型选择、权重比例都不公开。

黑盒层**不能**知道的元数据：

- ❌ 本项目评分维度（结构/内容/表达/可操作/格式）
- ❌ 本项目阈值（80/90）
- ❌ 本项目规则与上分规律
- ❌ 文章类型（入门/进阶/形式化）
- ❌ 文章系列编号（01/02/03）
- ❌ 前置文章与前置概念
- ❌ 评估模型的身份
- ❌ 权重比例

**作者可见的只有**：总分（0-100）+ 一句话理由（≤ 50 字）。

## 输入

- `article`（必需）：文章完整 Markdown 内容
- `platform`（必需）：目标平台（"wechat" / "blog" / "docs"）

## 输出

```python
class BlackboxResult:
    score: int          # 0-100
    reason: str         # ≤ 50 字理由
    model: str          # 评估模型标识（如 "gpt-4" / "gemini-pro"）
    timestamp: str      # 评估时间（ISO 8601）
```

## Prompt 模板（核心）

```
你是一位 <platform> 平台的主编，请评估下面这篇文章的发布价值。

只考虑读者体验：
- 这篇文章是否值得读者花时间阅读？
- 信息密度是否合适？
- 表达是否清晰？
- 有没有误导或错误？
- 对读者有没有实际帮助？

请打 0-100 分，并给出一句话理由（≤ 50 字）。

<article>
{article_content}
</article>

输出格式：
分: <0-100>
理由: <一句话>
```

**关键约束**：Prompt 中**绝不**出现本项目术语、阈值、规则。

## 关键设计

### 1. 异源模型

不能用与主项目同源的模型（不能用 Claude 系列）。

**原因**：
- 同源模型的训练数据可能包含本项目过往文章
- 同源模型可能"学到"本项目评分偏好
- 异源才能真正独立

**可选模型**（按优先级）：

| 模型 | 优势 | 劣势 |
| --- | --- | --- |
| OpenAI GPT-4o / GPT-5 | 通用强、API 成熟 | 成本高、中文一般 |
| Google Gemini Pro | 长上下文、多模态 | API 偶尔不稳 |
| DeepSeek-V3 | 中文优秀、成本低 | 国际可访问性 |
| 文心一言 / 通义千问 | 中文本地化 | 通用性较弱 |

### 2. Subagent 包装

调用黑盒层时，**必须**用 subagent 隔离：

- 避免主会话上下文污染（主会话可能已读过本项目规则）
- 避免作者通过主会话上下文推断黑盒规则
- 避免与白盒评分混淆

调用方式：

```python
Agent(
    description="blackbox-review of <article>",
    prompt=<Blackbox Prompt>,  # 上述 Prompt 模板
    subagent_type="general-purpose",
    isolation="worktree"
)
```

### 3. 不透露的元数据

黑盒层**不能**知道以下任何信息。如果作者想测黑盒层"会不会被针对性优化"，应该用一个全新的、不含本项目上下文的环境来跑。

### 4. 多次评分取中位数

同篇文章跑 ≥ 3 次黑盒评分，取中位数：

- 避免单次评分偶然性
- 防止作者对单一评分"运气"
- 让黑盒分数更稳定

```
score = median([score_run_1, score_run_2, score_run_3])
```

### 5. 评分随机性范围

允许 ±3 分的随机波动——这是黑盒评价的"自然噪声"。作者无法精确刷分。

## 校准流程

### 基线校准（与白盒分开）

黑盒层独立校准，**不**与白盒层同步：

1. 用 ≥ 10 篇已知质量的文章跑黑盒评分
2. 不同分数段都覆盖（高分 90+、中分 70-89、低分 < 70）
3. 画黑盒分数分布
4. 与白盒分布对比
5. 调整 Prompt / 模型选择，让两个分布**大致一致但不完全重合**
6. 不完全重合是关键——避免单轨评价失效

### 阈值校准

- 黑盒层独立阈值（建议 ≥ 75 通过，≥ 90 优秀）
- 与白盒阈值不同
- 必要时可调

### 长期回归（按月）

- 黑盒分 vs 实际阅读量、点赞、分享
- 调整模型权重（30/70 比例）
- 必要时换模型

## 与 content-review 的协同

### 调用顺序

```
1. 调用 content-review（白盒 30%）
   └─ 输出：详细报告 + 分数
2. 调用 blackbox-review（黑盒 70%）
   └─ 输出：总分 + 一句话理由
3. 加权平均：最终分 = 白盒 × 0.3 + 黑盒 × 0.7
4. 与发布阈值对比
   └─ ≥ 80：发布
   └─ < 80：拒绝，要求打磨后重评
```

### 反作弊机制

黑盒层的核心目的是防止"应试作文"。以下是关键反作弊设计：

| 设计 | 防什么 |
| --- | --- |
| Prompt 不透露规则 | 防针对规则刷分 |
| 异源模型 | 防单一模型偏置 |
| 不公开权重 | 防针对性优化 |
| 不公开阈值 | 防精确刷分 |
| ±3 分随机波动 | 防稳定刷分 |
| 多次评分取中位数 | 防运气刷分 |

### 协同而非替代

黑盒层不替代白盒层，两者互补：
- **白盒**告诉作者"哪里不好，怎么改"
- **黑盒**告诉作者"读者会不会接受"
- 最终分决定能否发布

## 反作弊机制详解

黑盒层的核心防御机制是**信息不对称**：

1. **规则不可知**：作者无法知道评分维度（content-review 的 5 维度）
2. **阈值不可知**：作者无法知道 80/90 阈值
3. **模型不可知**：作者无法针对特定模型的偏好优化
4. **权重不可知**：作者无法判断白盒/黑盒哪边更重要

**但有个悖论**：要让评分稳定，需要校准；要校准就需要数据；要数据就需要作者参与——这本身就会暴露信息。

**解决方案**：
- 校准阶段（< 10 篇样本）允许作者参与
- 校准完成后，**不再暴露**任何校准数据
- 作者只能看到自己文章的总分 + 理由

## 关于 SKILL 文件的可见性

**重要澄清**：本 SKILL.md 在仓库中，开发者可以读到。但这**不破坏**黑盒评价机制，因为：

| 暴露层级 | 暴露内容 | 是否破坏 |
| --- | --- | --- |
| **开发者读 SKILL** | Prompt 模板、调用方式 | ❌ 不破坏 |
| **作者读 SKILL** | 同上 | ❌ 不破坏 |
| **subagent 内部 Prompt** | 给模型的具体输入 | ❌ 不破坏（subagent 隔离） |
| **异源模型评分逻辑** | 模型的评估方式 | ❌ 不破坏（异源训练） |

**真正的不可见是**：

1. **异源模型的评估逻辑**——作者即使知道 Prompt 模板，也无法控制模型如何评分
2. **评分维度与阈值**——黑盒 Prompt 中**没有**这些信息
3. **白盒规则的隐式影响**——异源模型没有读过本项目规则

**这意味着**：即使作者读了 SKILL.md，也无法"针对评分优化"——因为评分由独立的异源模型按通用"发布价值"标准给出，不是按本项目规则给出。

如果项目未来要公开发布（如 SaaS 服务），需要将 blackbox-review SKILL 移到**私有仓库**，仅主项目保留接口契约。
